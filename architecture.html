Phase 1 · Hackathon build (alternate design)

Resource-level detection and explanation

Everything runs in AWS. Code computes every number; the agent is called only for flagged resources and explains them using read-only tools.

Triggers

  • Spend or unit-cost change over 30% and over $5/day vs baseline
  • Waste rule with flat cost: GetQueueUrl ≈ Send, empty-receive ratio high, wait time 0, provisioned ≫ consumed

Read-only boundary

  • Detect and Investigate roles only read CUR, CloudWatch and describe APIs
  • The output Lambda is the only thing that writes outside AWS
  • The agent sees computed figures, never table or message contents

Unit of analysis

  • One case = one table or queue ARN
  • Rows with no resource ID (e.g. DynamoDB Streams) are reported as unattributed so totals still match the bill
Phase 2 · Follow-up

Triage and service-level root cause

The AWS pipeline keeps doing detection. The investigation moves to a DevRev agent that can read code, so it can say which service owns the resource and what change in that service caused the cost.

From Phase 1Case file + resource-level findingPushed to DevRev by the output step instead of being filed directly
webhook / API
DevRev · workflow + agent
Step AMap resource → serviceSearch Terraform for the resource definition (workspace, module) and Helm / Marina values for services that reference the queue or table name. Normalize names: ARN vs name vs URL, env suffixes
service + repos
Step BFind what changed in the serviceCommits, merged PRs, Helm values and Terraform changes in the window where cost moved; deploy times. Read the consumer and producer code paths for the resource
candidate change
Step CExplain and triageLink the cost change to a specific change ("PR #123 added a GSI", "consumer replaced long polling"), propose the fix, route to the owning team's part, assign severity by $ impact
routed issue
DevRevIssue in owning team's queueEvidence: CUR numbers, metrics, the commit or PR, file and line
HumanTriage and closeTeam accepts, fixes or suppresses; status syncs back to the case table

Why DevRev for this part

  • Code, PRs and issues are already connected there, so no separate GitHub token or code index in AWS
  • Routing to parts and teams is native
  • Shows DevRev's own agent platform on a real problem

Boundary stays the same

  • Only the case file and finding cross into DevRev: computed numbers and resource names
  • Raw CUR and CloudWatch data stay in AWS

Feedback loop

  • Confirmed resource → service mappings are saved and reused in later runs
  • Suppressed findings feed back as rules so the same case isn't raised again
