CUR for cost attribution

What the Cost and Usage Report gives us, which columns matter for per-resource cost, where CloudWatch fills the gaps, and how much of the analysis to hand to an agent.

What CUR is

The Cost and Usage Report is AWS's line-item billing data. AWS writes it as Parquet (CUR 2.0) or gzipped CSV (legacy) into an S3 bucket we own and refreshes it up to about three times a day. Each row is one resource × usage type × operation × time window, with the usage quantity and its cost. Summed over a month, it matches the invoice.

  • Partitioned by billing month (BILLING_PERIOD=2026-10/). Each refresh overwrites that month's files, so always read the whole month folder.
  • Time granularity is the window each row covers. Pick hourly: it sums to daily, and it lets us line a cost change up with a deploy.
  • Recent data is provisional. The last 24–48 hours fill in late, and credits, tax and refunds land after month close. Treat D-2 as the newest settled day and recompute the last 3–5 days each run.
  • Covers only the account that creates it. A dev-account export sees only dev (020040093233). Prod later needs an export from the management account.
Export settings

Standard data export · CUR 2.0 · Include resource IDs: on · Hourly · All columns · Parquet · Overwrite. One export for all services; filter to DynamoDB and SQS at query time so reconciliation still sees the full bill.

Already available for history: Umang's legacy CUR at s3://umang-bucket-test/monthly/TestReportLambda-Umang-Daily/ (daily, resource IDs on, Sep + Oct).

Do we also need CloudWatch?

Yes, but only to explain changes.

CUR answers how much and which billing line. It cannot say why, because it only knows billed units, not what the application did. CloudWatch supplies the denominators.

Metrics that explain a cost increase

Every request-priced cost line splits into a volume part and a per-unit part. Find which part moved first, then use the metrics below to name the cause.

cost = requests × billed units per request × price
       └ volume ┘   └──── efficiency ────┘

volume up, efficiency flat   → more traffic (expected, or a retry storm / new caller)
volume flat, efficiency up   → bigger items, GSIs, scans, empty receives: the waste case

Where the agent fits

Don't run the agent over raw CUR every day, and don't leave it as a manual step either. Let deterministic code find the candidates, and call the agent only to explain them and write the issue.

Tier 1 · Code, daily

Detect

Per resource, compare settled day vs same weekday last week and vs the 4-week same-weekday median, for spend and unit cost. Flag when the change is over 30% and over $5/day.

Tier 1 · Code, daily

Waste rules

Fixed checks that need no baseline: GetQueueUrl ≈ Send, empty-receive ratio high, wait time 0, provisioned ≫ consumed, PITR on idle tables.

Tier 2 · Agent, on flags

Explain and file

For each flag, the agent gets the computed numbers plus CloudWatch series and recent deploys, names the likely cause, estimates savings and drafts a DevRev issue for the owner.

Why split it this way

  • Numbers stay defensible. Detection and dollar figures come from code, so they reconcile. The agent only reasons over figures it is given.
  • Cost and noise stay bounded. Thousands of resources reduce to a handful of flags a day.
  • The agent does what code can't: connecting a WCU jump to an item-size change and a deploy, and writing a clear issue.
  • Humans approve at first. In shadow mode the agent drafts issues for the platform team to review; auto-filing comes later.

Agent tools (all read-only)

get_resource_cost(resource_id, days)        # from CUR, by usage_type + operation
get_baseline(resource_id, metric)           # same-weekday median, D-7
get_cloudwatch(resource_id, metrics, days)  # empty receives, consumed units, sizes
describe_resource(resource_id)              # queue attributes, table mode / size
get_owner(resource_id)                      # tags, then Terraform / Marina
get_deploys(service, window)                # deploy timestamps
file_devrev_issue(owner, title, evidence)   # only write action, gated
